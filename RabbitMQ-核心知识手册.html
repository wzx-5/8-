1 为什么要用消息队列（MQ）

先搞清楚「为什么」，再学「是什么」。MQ 的三大核心价值 + 引入它的代价。

① 异步

响应更快

下单后不用同步等短信/积分/日志，直接返回「成功」，耗时从 1s → 50ms。

② 解耦

互不影响

订单系统发一条消息，短信/库存/积分各自订阅。新增一个下游，上游代码零改动。

③ 削峰

保护下游

秒杀瞬间 1 万请求全打进 MQ 排队，数据库按自己的能力慢慢消费，不会被打挂。

⚠️ 引入 MQ 的代价（面试常被追问）
系统复杂度上升（多一个组件要运维）、消息丢失、消息重复、消息乱序、数据一致性（从强一致退化为最终一致）。这也是本手册第 6、11 章重点解决的问题。

你刚学完 Redis，MQ 和「Redis 当消息队列」怎么选？

Redis 的 List / Stream / Pub-Sub 能做轻量 MQ，但不保证可靠投递（Pub/Sub 丢消息、List 无 ACK 机制）。Redis 适合：内部小规模、允许丢消息、要极高性能。RabbitMQ 适合：对可靠性和路由有要求的正式业务。具体交集请看下面的韦恩图。

1.1 Redis vs RabbitMQ 韦恩图

你刚学完 Redis，用韦恩图记住两者的关系：有交集，但定位不同。

图 1 · Redis（左）与 RabbitMQ（右）的定位：交集=都能做消息，差异=可靠性与路由能力
✅ 一句话记忆

Redis 是「带队列功能的数据库」，RabbitMQ 是「带数据库功能的队列」。要性能选 Redis，要可靠性、路由、确认机制选 RabbitMQ。

2 核心概念：先记 8 个名词

RabbitMQ 里几乎所有概念都能在「生产 → 中转 → 消费」链路里找到位置。

名词一句话解释类比（现实）易错点
Producer生产者，发消息的一方寄件人—
Consumer消费者，收消息的一方收件人—
BrokerRabbitMQ 服务器本身快递中转站—
Exchange交换机，消息的路由中转分拣中心消息不能直发 Queue，必须过 Exchange
Queue队列，消息真正存储的地方收件箱持久化队列 ≠ 消息持久化
BindingExchange 与 Queue 的绑定关系投递路线路由靠 binding 里的 routing key
VHost虚拟主机，逻辑隔离/权限隔离快递分区不同业务用不同 vhost 隔离
Connection / ChannelTCP 连接 / 连接内的逻辑信道公路 / 车道Channel 复用 TCP，不要每条消息建连接
💡 关键细节：Connection vs Channel

一个 TCP Connection 上可以建立多个 Channel（信道），多个线程各用一个 Channel，共同复用同一条 TCP。理由：创建/销毁 TCP 开销大。Spring AMQP 默认已帮你做了连接池。

💡 关键细节：默认交换机

Exchange 名称为空字符串的默认交换机是 direct 类型，它把消息路由到 routing key = 队列名 的队列。所以「直接发到队列」其实仍是经过交换机，只是用了默认交换机。

4 交换机（Exchange）四种类型

RabbitMQ 的路由能力全靠 Exchange。四种类型=四种「分拣规则」。

类型路由规则典型场景面试权重
Direct 精确routing key 完全匹配点对点、按级别路由（error 队列只收 error）⭐⭐⭐
Fanout 广播忽略 routing key，广播给所有绑定队列群发通知、日志全量存档⭐⭐⭐
Topic 通配通配符：* 匹配一个词，# 匹配零或多个词按主题订阅（order.create.*）、日志分级筛选⭐⭐⭐
Headers 属性按消息 header 匹配（x-match all/any）几乎没有场景⭐ 认识即可
💡 Topic 通配符记忆

* = 占一个位置（一个单词）；# = 占任意多位置。例如 *.orange 能匹配 fast.orange，#.orange 还能匹配 a.b.orange。注意 *.orange 不能匹配只有一个词的 orange。

4.1 Direct / Topic / Fanout 关系韦恩图

三种核心交换机的关系：Direct 和 Topic 都靠 routing key 路由，Fanout 完全不管 key。

图 3 · Direct 与 Topic 共用「routing key」机制，Fanout 独立；三者的共同点是都要绑定 Queue 才会投递
Direct：精确定向 Topic：通配筛选 Fanout：无差别广播

怎么选？

  • 规则确定、无需过滤 → Direct（最快、最简单）
  • 需要按主题/多条件筛选 → Topic（direct 能做的 topic 都能做，只是更重）
  • 要所有消费者都收到同一份消息 → Fanout（发布订阅）

5 六种官方消息模型

官网把使用方式归纳为 6 种。前两种不用交换机（默认交换机），后四种都靠交换机。

模型拓扑要点
1 简单队列1 生产者 → 1 队列 → 1 消费者入门模型
2 工作队列 面试重点1 队列 → 多消费者（轮询 / 公平分发）prefetch + 手动 ACK 避免忙闲不均
3 发布订阅Fanout 交换机 → 多队列 → 各自消费每个消费者一个队列，互不抢消息
4 路由Direct 交换机 → 按 routing key 定向只有 key 匹配的队列收到
5 主题Topic 交换机 → 通配符匹配最灵活，常用于日志分级
6 RPC请求队列 + 响应队列 + correlationId客户端等服务端返回，靠 correlationId 关联
💡 Work Queue 两大要点（高频追问）

① 默认是轮询（round-robin）：消息平均分给每个消费者，但「能力强的消费者」不会多干——会出现一个忙死、一个闲死。

② 公平分发（Fair Dispatch）：设置 prefetchCount = 1，消费者处理完并 ACK 后才取下一条，谁快谁多干。这就是 QoS（限流） 的雏形。

6 可靠性三层保障（面试必考）

「如何保证消息不丢」是面试第一大题。答案就是三段式：生产端确认 → 存储端持久化 → 消费端 ACK。

图 4 · 可靠性三层：任何一层出问题都丢消息，三层都做好才叫「不丢」

细节与坑

  • autoAck 是万恶之源：自动 ACK 表示「收到即确认」，消费者正在处理、还没处理完，消息就从队列删了。宕机 = 消息丢。
  • 持久化 ≠ 100% 不丢：持久化是先写缓冲区再落盘，极端断电仍可能丢。要强保证用「持久化 + 仲裁队列 + 生产 Confirm」。业务可接受再放宽。
  • Confirm 三种模式：none（不确认）、simple（每条同步等确认，慢）、correlated（异步批量，推荐，性能最好）。
  • 重试要谨慎：消费失败立刻重试且无上限，会把异常消息反复消费、堵死队列。要么有限次重试 + 进死信，要么用 Spring 的 @Retryable。
✅ 背下来的一句话回答

「消息不丢 = 生产者 Confirm + 交换机/队列/消息三持久化 + 消费者手动 ACK，消费失败有限重试进死信队列。」

7 死信队列 DLX 与延迟队列

死信队列是「垃圾回收站」，延迟队列通常就是「TTL 过期 + 死信转发」拼出来的。

死信队列 DLX

垃圾回收站

消息变成死信的 3 个条件：① 被拒绝且 requeue=false、② TTL 过期、③ 队列满了。

死信 → 转发到 x-dead-letter-exchange 指定的交换机

延迟队列

TTL + DLX

消息设置 TTL 过期时间 → 过期变死信 → 死信交换机转发到「真正要处理的队列」→ 消费。实现「N 秒后执行」。

场景：订单 30 分钟未支付自动取消

死信队列配置（核心片段）

// 正常业务队列，声明其死信转发目标
Map<String,Object> args = new HashMap<>();
args.put("x-dead-letter-exchange", "exchange.dlx");   // 死信去哪个交换机
args.put("x-dead-letter-routing-key", "order.cancel"); // 死信用什么路由键
new Queue("order.queue", true, false, false, args);
// 死信交换机 + 死信队列照常声明，消费者监听死信队列即可
⚠️ 延迟队列的经典坑（3.x 老版本）

同一个 TTL 队列里，排在队头的消息会阻塞后面所有消息的过期（只有队头过期才会继续判后面的）。解决：每条消息单独设置 TTL（per-message TTL），或按延迟档位拆多个队列。RabbitMQ 3.x 还有官方插件 rabbitmq_delayed_message_exchange，直接用延迟交换机更省心。

8 集群与高可用

单机挂了一切都完。三种模式，从「开发环境」到「生产推荐」。

模式数据怎么存故障恢复适用
普通集群 Classic 多节点共享元数据（交换机、队列定义），但队列消息只存一个节点，其他节点只是指针 存消息的节点宕机 → 消息丢失 开发 / 测试环境
镜像队列 Mirror 队列在多个节点全量镜像，主写从同步 主节点宕机 → 从节点顶上 旧生产（3.8 之前）
仲裁队列 Quorum 基于 Raft 协议多副本，写多数节点成功才算成功 多数副本存活即可自动选主 ✅ 新项目推荐
✅ 选型建议

新项目直接 仲裁队列（Quorum Queue）：强一致、自动故障转移、不依赖外部组件。镜像队列因为性能差、有脑裂风险已逐渐被淘汰。再配合客户端负载均衡 + 多节点部署达到高可用。

⚠️ 网络分区（脑裂）

集群节点间网络断开时会出现分区。仲裁队列通过 Raft「多数派」避免双主；镜像队列历史上有脑裂（两个主同时写）风险。生产应开启分区自动恢复策略。

9 RabbitMQ / Kafka / RocketMQ 对比

面试最后一道常考题：为什么选 RabbitMQ 而不是 Kafka？ 用韦恩图 + 表格讲清楚。

图 5 · 三者都是「消息中间件」，定位差异在吞吐量 vs 功能丰富度
RabbitMQ：万级 · 功能全 · 可靠性强 Kafka：百万级 · 高吞吐 · 日志流 RocketMQ：十万级 · 事务消息

怎么选（面试标准答案）

  • 业务系统之间的解耦 / 订单、通知、异步任务（对可靠性、路由要求高，吞吐万级就够）→ RabbitMQ
  • 海量日志、埋点、大数据流处理、指标上报（要超高吞吐，可容忍少量重复/乱序）→ Kafka
  • 要分布式事务消息、延时消息，且团队是 Java 栈 → RocketMQ（很多大厂自研的选它）

10 典型业务场景

把前面所有知识点放进真实业务里，看怎么串起来。

异步解耦

下单成功 → 发 MQ → 短信/积分/优惠券/日志各自消费。新增下游零改动。

削峰填谷

秒杀：请求先入 MQ，后台按速率消费。Redis 预扣库存 + MQ 异步落库，保护数据库。

延迟任务

订单 30 分钟未支付自动取消、活动定时提醒、限时优惠。用 TTL + DLX。

分布式事务

RabbitMQ 无内置事务消息，用 本地消息表 + MQ 实现最终一致性：本地落库 + 消息表同事务，再发 MQ，消费者幂等。

日志收集

多个服务日志 → Topic 交换机分级 → 归档 / 告警队列。

✅ 秒杀完整链路（背这个案例）

前端限流 → Redis 原子扣减库存 → 扣减成功则发 MQ → 后台消费者异步生成订单/减库存落库 → 失败进死信队列人工补偿。既保证体验（秒回），又保护数据库不被瞬间打挂。

11 四大经典问题与解决方案

面试连环问：丢消息、重复、乱序、积压——这四件事，就是引入 MQ 后真实会踩的坑。

① 消息丢失怎么办

答案就是第 6 章的三层保障，这里给一个兜底方案：

  • 对账机制：定期扫描「本地消息表」，把超过 N 分钟仍未确认投递成功的消息重新发送。
  • 落库优先：业务数据先落库，发 MQ 只是「通知」，即使丢了也能靠数据重建。

② 消息重复消费怎么办

网络抖动、ACK 超时重投，重复消费无法从源头避免，只能让消费逻辑幂等：

方案思路适用
数据库唯一约束用业务主键 / 消息 ID 建唯一索引，重复插入报错被忽略落库型消费
Redis SETNX处理前 SET key NX EX 120 占位，重复消息直接跳过通用去重
业务状态机如订单「已支付」状态，重复的「支付通知」直接忽略有状态业务
去重表专门一张消费记录表，唯一键 = 队列 + 消息 ID严格幂等

③ 消息乱序怎么办

⚠️ 关键认知：多消费者抢一个队列 = 天生乱序

因为每个消费者各拉各的，处理速度不同，先发的可能后处理。要让消息有序，只有三种办法：

  • 单队列 + 单消费者：最简单，天然有序，但吞吐受限。
  • 按业务 key 路由：把 routing key 设计成业务 ID（如订单号），让同一订单的所有消息进同一个队列，该队列单消费者处理。
  • 消费端排序：消息带序号，消费者缓存乱序消息，凑齐后按序处理（代价大，慎用）。

④ 消息积压怎么办

临时扩容

横向多开消费者实例，提高吞吐。注意队列预取数、下游限流配合。

转储再处理

写一个消费者把积压消息转移到一个新临时队列，再慢慢处理；原队列马上腾空，避免堆积拖死。

治本排查

查消费者慢在哪：慢 SQL？死循环？依赖的下游故障？修复后自然消化。

12 面试高频题库（折叠答案）

先自己想答案，再点开对照。带 必背 的要能口头流畅讲出。

必背为什么用消息队列？有什么缺点？

优点：① 解耦：上下游独立变更；② 异步：缩短响应时间；③ 削峰：缓冲高并发保护下游。

缺点：系统更复杂、消息可能丢失、重复、乱序、数据一致性从强一致变最终一致。

必背如何保证消息不丢失？

三段式：生产端 Confirm（确认落盘，失败重发）→ 存储端持久化（Exchange + Queue + Message 三处 durable，生产用镜像/仲裁队列）→ 消费端手动 ACK（处理成功才确认，失败有限重试进死信）。加对账补偿兜底。

必背如何保证消息不重复消费？

无法杜绝重复，只能幂等。方案：数据库唯一约束、Redis SETNX 去重、业务状态机判断、独立去重表。关键是有个能唯一标识一条消息的东西（消息 ID / 业务主键）。

必背如何保证消息有序？

多消费者并发消费天然无序。方案：① 单队列单消费者（牺牲吞吐）；② 按业务 key 设计 routing key，同一实体进同一队列；③ 消息带序号消费端重排。

必背消息积压了怎么解决？

排查消费慢的原因（慢 SQL / 下游故障）；临时扩容消费者；写转储任务把消息移到新队列慢慢处理；必要时上游限流/降级。积压本质是「消费能力 < 生产速度」。

必背Exchange 有哪几种类型？区别？

Direct（routing key 完全匹配）、Fanout（广播忽略 key）、Topic（通配符 * # 匹配）、Headers（按 header 属性，几乎不用）。

必背什么是死信队列？延迟队列怎么实现？

死信队列：接收「死信」消息的队列。消息变死信三个条件——被拒绝且 requeue=false、TTL 过期、队列满。延迟队列 = TTL + 死信转发：消息设过期时间，过期成死信转到目标队列再消费；或用官方延迟交换机插件。

必背生产端怎么确认消息送达？Confirm 和事务的区别？

开启 publisher confirm，Broker 落盘成功回确认，失败走回调重发。事务机制（txSelect）每条消息同步 commit，性能差很多，几乎不用。Confirm（correlated 模式）性能好，是推荐方案。

必背消费端 ACK / NACK / Reject？autoAck 为什么不好？

处理成功 basicAck；处理失败 basicNack（可 requeue 重回队列）；basicReject 是 Nack 的单条版。autoAck 收到即删，消费者宕机或处理异常时消息就丢了，所以生产必须手动 ACK，且业务处理完才 ACK。

什么是 prefetch？有什么用？

消费者单次预取的消息数量。prefetch=1 时消费者处理完一条再取下一条，实现公平分发，避免「一个忙死一个闲死」，也是对下游的简单限流。值太大 = 消费者本地囤积消息。

Connection 和 Channel 的区别？

Connection 是 TCP 长连接，Channel 是连接上的逻辑信道，一个连接可开多个 Channel，多线程共用连接并发发送，避免反复建连的开销。

镜像队列和仲裁队列区别？生产怎么选？

镜像队列：主从全量同步，异步，有脑裂风险。仲裁队列：Raft 多副本强一致，写多数节点成功，自动选主。新项目推荐仲裁队列。

RabbitMQ 和 Kafka 怎么选？

RabbitMQ：万级 QPS、功能全、路由灵活、可靠，适合业务系统间解耦异步。Kafka：百万级 QPS、顺序写盘零拷贝、日志/流处理/埋点，适合海量吞吐场景。RocketMQ 折中，支持事务消息，Java 大厂常用。

一条消息从发送到消费的完整流程？

Producer 建立 Connection/Channel → 发送消息到 Exchange（带 routing key）→ Exchange 按类型+key 匹配 Binding → 投递到目标 Queue → Queue 持久化暂存 → Consumer 拉取/被推送 → 处理成功后 ACK → 消息删除。中途任一步配合持久化 + 确认机制才可靠。

mandatory 参数是干什么的？

mandatory=true 时，消息发到交换机却没有匹配到任何队列，会把消息回退给生产者（ReturnListener 回调），避免静默丢失。它是「发送即丢弃」的保护伞。

如何给 RabbitMQ 做限流 / 抗压？

消费端：prefetch 限制单消费者预取量；全局消费者并发上限。生产端：发送前做令牌桶限流 + 对账补偿。缓存层用 Redis 兜底。下游数据库加保护（连接池/熔断）。

13 代码与配置速查（Spring Boot）

看完理论上手就能用。最常用的三段：配置、发消息、收消息。

① application.yml 关键配置

spring:
  rabbitmq:
    host: 127.0.0.1
    port: 5672
    username: guest
    password: guest
    publisher-confirm-type: correlated      # 生产端异步确认
    publisher-returns: true              # mandatory 回退
    listener:
      simple:
        acknowledge-mode: manual         # 手动 ACK（关键！）
        prefetch: 1                          # 公平分发
        retry:
          enabled: true
          max-attempts: 3                   # 有限重试，别无限重试

② 生产者发送 + 确认

@RestController class OrderController {
    private final RabbitTemplate rabbit;

    public void createOrder(OrderDTO dto) {
        // 1. 业务落库（本地消息表一并写入）
        orderService.insert(dto);
        // 2. 发消息：交换机 + 路由键 + 消息体
        rabbit.convertAndSend("exchange.order", "order.created", dto);
        // 3. 异步确认结果：ConfirmCallback 里失败则补偿重发
        rabbit.setConfirmCallback((corr, ack, cause) -> {
            if (!ack) log.warn("发送失败: {}", cause);   // 补偿
        });
    }
}

③ 消费者手动 ACK

@Component class OrderConsumer {
    @RabbitListener(queues = "order.queue")
    public void handle(Order order, Channel channel, @Header(AmqpHeaders.DELIVERY_TAG) long tag) {
        try {
            orderService.process(order);            // 先做业务
            channel.basicAck(tag, false);          // 成功才 ACK
        } catch (Exception e) {
            if (canRetry(tag)) channel.basicNack(tag, false, true);  // 重回队列重试
            else channel.basicNack(tag, false, false);               // 进死信队列
        }
    }
}

✅ 三个「背下来」的排障口诀

① 丢消息 → 查 Confirm 是否开、持久化三件套、是否 autoAck。
② 重复消息 → 消费逻辑加幂等（唯一键/状态机）。
③ 积压 → 查消费者慢在哪，扩容 / 转储，最后考虑上游降级。
